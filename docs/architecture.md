# How Reapers is built

## The shape

```
reapers/
├── reapers_shared/   Rules, catalogues and reaper generation. Pure Dart.
├── reapers_flutter/  The game.
├── reapers_server/   The Serverpod backend.
├── reapers_client/   Generated by Serverpod. Never edited.
├── art/blender/      The scripts every 3D model is built from.
├── tool/             Art and asset builds, written in Dart.
└── docs/
```

It is one Dart pub workspace. Flutter and Dart are pinned by `.fvmrc`.

## One rule, written once

Everything that decides an outcome lives in `reapers_shared` and nowhere else: how a hunt plays, what a class is worth, what a refusal is, how a rift is sealed. The game runs those rules to play offline. The server runs the very same code to judge an online player. There is no second implementation to drift.

Three types carry most of it:

- **`PlayerState`** is everything a player owns and has done, as one immutable value. Each thing a player can ask for is a method that returns the next state or throws a `RuleBreach` naming a `Refusal`. It reads no clock and rolls no dice: seeds and times are passed in, so the server decides them for an online player.
- **`ReaperState`** owns one reaper's fixed genome, experience, equipment, codex, soul memories and records. `ReaperSoul` derives the permanent birth gift and temperament from R1 fields. `SoulRules` combines the gift's preferred memory with level to derive its awakening; `HuntStats` and `HuntSim` execute it. `PlayerState` owns the roster, selection and account currency. Schema three migrates the old single reaper without resetting it. Missing memory fields begin at zero. The starter is non-tradable; an NFT reaper is identified by its Core asset address.
- **`HuntSim`** is one encounter, advanced a tick at a time from quantised inputs (aim in hundredths of a degree, turn speed in thousandths of a radian a second). A husk has a real position around the player, in metres, and moves through it: along the floor or through the air, inside the `HuntPlan` it was given. The same seed, the same plan and the same inputs always end the same way, on any device.

That determinism prevents a client from inventing a result or submitting its own growth counters. It does not prove a human performed the inputs: a bot can produce a valid log. The phone records the plan and each tick's input into a version-six `HuntLog` (9 bytes for the plan and the difficulty, 72 more when the room was surveyed and 153 more for what stands in it, then 8 a tick, which say whether the art was held, and 4 more per tap) and sends that, not a result. The server replays it and pays whatever the replay earns, including bounded soul marks on successful absorption. It replays with windows 3% wider than the phone played with, so a hunt won by a hair is never lost to rounding. Impossible aim ranges, overlong logs and a plan too narrow to be fair are refused. A different combat-log version receives an update refusal.

Staging and production also refuse the simulated acquire, release, hunt-settlement and rift endpoints. The invented mints, balances and unverified group reports cannot become live NFT growth accidentally. Replacing this gate requires verified husk ownership, escrow, confirmed burns and authoritative rift results, as described in [nfts.md](nfts.md). [The soul research](research/reaper-identity-and-growth.md) records the design evidence; [launch readiness](launch-readiness.md) separates implemented behaviour from the dependencies still missing.

## The game

```
lib/
├── app.dart, main.dart
├── theme/veil.dart        Colour, type and spacing tokens.
├── widgets/               The "funeral ledger" interface kit.
├── screens/               Threshold, oath, sanctum, vault, armory, codex, rifts.
├── hunt/                  The arena, the HUD, the pose sources, the hunt screen.
├── rift/                  The rift screen.
├── render/                3D: reaper and husk rigs, looks, lighting.
├── src/backend/           Who keeps the books: the phone, or the server.
├── src/state/             Riverpod providers.
└── l10n/                  Strings. No screen hardcodes text.
```

**Backends.** Screens read the player from one Riverpod notifier, which asks a `GameBackend`. `LocalBackend` keeps the books in shared preferences and is the whole game with no server. `ServerBackend` sends the same requests to Serverpod. Which one a build uses is decided by `--dart-define=REAPERS_SERVER_URL=…`; without it the build is fully offline.

**Studio.** `main_preview.dart` runs `ReaperStudio` without preferences, authentication or a backend. It uses `ReaperStage`, `ReaperGenome` and the same `Progression`, equipment and strike arithmetic as the game. Its absorption button is explicitly illustrative. It is also accessible from the sanctum and replaces the developer-only gallery. Model changes are serialized and superseded loads cannot mount after disposal; auto rotation respects reduced motion.

**Wallets and NFT reapers.** `SolanaEndpoint` creates short-lived, single-use challenges scoped to the authenticated guest, domain, chain and address. Kit verifies the exact Ed25519 signature; Mobile Wallet Adapter signs it on Android. The first proof links the guest; subsequent proofs restore that wallet's existing account without merging saves. Authentication remains Serverpod's token service. The real wallet balance is separate from the husk market's simulated SOL.

Before an NFT-bearing player's mutation, `ReaperLedger` reads finalized ownership through Kit RPC and decodes Core accounts with Kit's Metaplex Core package. It validates program, collection, owner and the configured genome URI. Chain genesis is checked as well. Canonical `ReaperRecord` rows are locked in address order, and growth and player state commit together. Import starts at level one, never with submitted or offline growth; a transfer retains that asset's canonical growth. A failed RPC leaves the books intact and fails the action. Ownership is a finalized snapshot, not atomic with a subsequent on-chain transfer. [solana.md](solana.md) documents the contract and deployment settings.

**Arrival.** The native Android/iOS splash and the first Flutter frame use the same `splash_mark.png` on the veil's ink. `SplashGate` preloads that still, then draws one 1.8-second reaping arc and reveals the wordmark. Reduced motion holds a still for 250 ms. The mounted game cannot tick, receive focus, touches or accessibility focus until arrival ends. A four-second ceiling reveals the loading or recovery screen even when the keeper is slow. See [branding.md](branding.md) for the masters and rebuild command.

**The arena.** `HuntArena` owns the scene, the husk and the phone's pose, and shows whatever `HuntSim` it is given. A lone hunt and a seat in a rift are both fought in it. Screens lay their own words over it.

**Drawing the husk out.** Before a hunt, the player traces the husk's `Sigil`: lights around them that catch in order. The sigil is a rule, so it lives in `reapers_shared`: `Sigil.draw` lays one out from the hunt's seed and the rarity's `SigilShape`, and `SigilTrace` follows the phone across it, reading no clock. On the phone, `SigilPainter` hangs it in the room and `ScanOverlay` lays the words and a flat drawing of it over the top.

**Reading the room.** While the sigil is traced, a `RoomSurvey` reads the room, and when the last light catches, `sigilPlan` asks it for a `HuntPlan` over the arc the sigil covered: how far down the floor is, and how far the way is clear in each direction. `openRoomSurvey` gives a `DepthSurvey` on a phone that can see, and nothing anywhere else. Frames from `HuntCamera` are cut down by `CameraPicture`, run through `DepthModel` (Depth Anything V2 small, on the phone, through ONNX Runtime), and put together by `RoomMap`. `RoomMap` is plain arithmetic with no camera or model in it, so it is tested against rooms drawn by hand.

The same pictures make an `OcclusionMap`: how far the nearest thing is in every direction. The arena masks the 3D scene with it through `assets/shaders/occlusion.frag`, so a husk that ducks behind the counter is hidden by it. The plan also says how tall what stands in each direction is, whether its top is a ledge and where to hide behind it, and `HuntSim` has the husk leap onto and behind things from that.

Anything that learns more about the room (ARKit, ARCore, a server that names what it sees) is another survey and hands the hunt a better plan. See [environment.md](environment.md).

**The lens.** `CameraOptics` asks the phone for its camera's focal length and sensor size, and the hunt is drawn with the field of view that follows from them. A husk seen through a different lens from the floor it stands on slides across the floor when the phone turns.

**Where a rift stands.** A rift's `RiftRoom` holds one `GeoPoint` for its husk and every `RiftFrame` carries it, so whoever hosts the room is the one place that knows where the enemy is. On the phone, `Whereabouts` says where the phone is, the pose source says where north lies in the view (`AttitudeFilter` listens to the magnetometer for that and nothing else), and `RiftPlacer` turns the three into a `RiftSighting`: the direction and distance this reaper sees the husk at. `RiftPlacer` has no sensors in it and is tested with two phones side by side.

`GeoFix` carries the device observation time and accuracy alongside its point. Shared rules validate it with a supplied clock. `LocationTracker` owns the foreground subscription, expiry timer and one serial, latest-only upload queue. It cancels GPS and clears the remote reading when inactive or disposed. `DeviceWhereabouts` uses foreground-only Apple settings and has explicit permission/service failures; the gathering screen explains these and offers Settings or retry. The server validates again before accepting a location or a rift standing. GPS course is not used as a compass.

**Music.** `Soundtrack` decides which piece plays and how it is heard, and a `ScoreEngine` makes the sound. The real engine is SoLoud, handed in at startup; everywhere else, including every test, the engine is silent. `sigilMix` and `huntMix` are the whole of how a hunt sounds: pure functions from the sigil's and the hunt's state to a loudness and a veil. The recordings are other people's, built by `tool/build_music.dart` and credited in `assets/music/CREDITS.md` and on the colophon page.

**Pose.** Where the phone points comes from a `PoseSource`. `DevicePoseSource` fuses the gyroscope and accelerometer; `DragPoseSource` follows a finger on simulators; `AdaptivePoseSource` uses the device when it answers and the drag when it does not. ARKit and ARCore would be a fourth source behind the same interface.

**3D.** Rendering is `flutter_scene` on Flutter GPU (Impeller). Three custom materials in `assets/materials/` do most of the visual work:

- `reaper.fmat` draws every part of every reaper. A model's vertex colours are masks, not colours (grime, char, wear, hollow), so an outfit is a handful of shader numbers rather than another model: the same cloth is dyed, charred from the hem up, then eaten away.
- `husk.fmat` draws a husk's surfaces in an NFT's colours, lights its eyes and seals, and dissolves it. On a rift's husk it also carries the collection's portraits.
- `shadow.fmat` is the soft dark patch under a husk that stands on the floor.

**Creatures.** A husk's creature is not skinned. It is built from rigid parts on named pivots, and `HuskRig` moves the pivots from what the rules say the husk is doing: legs swing as fast as it is going, wings beat, the jaw drops as it draws breath, the head turns to watch the player.

**Reaper animation.** All six reaper GLBs contain 64 named Blender clips: spirit and humanoid performances for 32 states. The rig separates chest and pelvis, with neck, arm and leg joints. `ReaperMotion` is the shared presentation catalogue; `ReaperAppearance.clipName` selects the form's performance and `ReaperPlayback` drives the same elapsed time into Flutter Scene and the browser mixer. The studio exposes selection, scrubbing and contact poses. Cloth motion follows that clock while preserving genome morphs. This is an articulated rigid-part rig, with class-specific gesture sizes and hand adaptations. It changes no combat outcomes. See [animations.md](animations.md).

Models and materials are compiled by the build hook in `hook/build.dart`, so changing one needs a full `flutter run`, not a hot restart.

**Forms and expressions.** Reaper models include a spectral body, optional articulated legs and six facial expression morphs per head. Blender bakes face weights and leg poses into the body clips. `ReaperAppearance` and `reaperPartVisible` share the wardrobe and form visibility contract between native and web; robe shortening remains separate from clip playback. The studio exposes all held objects independently of class progression, with empty hands disabling weapon attacks. These controls are unsaved previews and do not alter NFT genomes, equipment permissions or combat rules.

**Browser studio.** Supported targets are web, Android and iOS. `main_preview.dart` opens the isolated studio on each; the camera game targets Android and iOS. `ReaperStage` conditionally exports the mobile Flutter GPU portrait or a WebGL 2 portrait. The web portrait loads the same models and adapts the authored `reaper.fmat` fragment to a lit material, including its vertex masks, burn front and hollowing. Colour uniforms convert from sRGB to linear light, as the native material's `source_color` hint does. Calling changes release the previous model; cached trait changes update uniforms and morph weights. Web does not import the native GPU scene, read preferences, or open a wallet.

**Simnet.** `--dart-define=REAPERS_SIMNET=true` swaps the keeper for a `SimnetBackend`: a `LocalBackend` under its own save, which posts an airdrop, a buy, an escrow and a receipt-carrying burn to a `SimnetChain` on the phone after the rules allow each one. `SimnetToasts`, laid over every screen in `MaterialApp.builder`, confirms each transaction; `SimnetScreen` is its explorer. It is for showing the chain before a program exists. See [solana.md](solana.md#the-simnet).

**Autoplay.** `--dart-define=REAPERS_AUTOPLAY=true` has a simulated player fight every hunt and rift. It is how the game can be watched on a simulator, which has no gyroscope.

## Art

There are no hand-made model files. Every reaper, weapon and husk is built by a Python script run inside headless Blender, driven by `dart tool/build_art.dart`. The husk scripts read their dimensions and seal positions from the shared `Vessel` enum, and fail the build if a creature does not fit them, so the model and the hit-testing cannot disagree. The same build renders every NFT's portrait from its creature and its look. See `art/blender/README.md`.

## The server

Serverpod 4, with its embedded Postgres in development and tests.

- **Sign-in.** A fresh install plays as a guest (the anonymous identity provider) so nobody signs up before their first hunt. Android wallet proof links that guest, or restores the wallet's existing account.
- **`PlayerEndpoint`** stores each player's `PlayerState` whole, in one row. Every request locks the row, applies one shared rule and stores the result (`PlayerBooks.change`). No method takes a player id from the client.
- **Location.** `updateLocation` and `location` require authentication and use the same player row. Only the latest `GeoFix` is kept; out-of-order updates are ignored, null clears it, and stale readings are never returned. This is positioning, not proof of physical presence: coordinates reported by a modified client remain untrusted.
- **Receipts.** When a hunt is absorbed, the server rolls how well the reaper fed and signs the result with Ed25519 (`ReceiptSigner`), in the fixed 98-byte layout of the shared `AbsorptionReceipt` a Solana program could verify. See [nfts.md](nfts.md).
- **`RiftEndpoint`** is one streaming call per reaper: frames come down, the reaper's reports go up. `RiftHall` keeps the open rifts in memory and moves each on ten times a second.
- **Refusals** cross the wire as a `Refused` exception carrying the shared `Refusal`'s name, so an online player is told exactly what an offline one would be.

Secrets are never committed. `config/passwords.yaml` is git-ignored and created from `passwords.example.yaml`; a deployed server reads `SERVERPOD_PASSWORD_<name>` from its environment and refuses to start in staging or production without them, the receipt signing secret included.

## Rifts

`RiftRoom` (shared) is the keeper of what a circle shares: who is in it, the ward, the phases, the verdict. Like the hunt it reads no clock; its host calls `advance` as time passes. The phone hosts a room itself when offline (`LocalRiftSession`), and the server hosts rooms for many (`RiftHall`). Both are thin.

Each reaper runs their own `HuntSim` in rift mode on their own phone and reports a running total of the damage they have dealt. Reports are whole standings, not changes, so one that is lost, repeated or late never miscounts. A phone shows its own strikes at once by subtracting what the room has not yet heard of. The shrieks come from a seed-only timetable, so every phone in the circle is told to hold still at the same moment.

Shades are the same simulated player the tests use, stepped by the room.

## Known limits of this design

- **The room is read once, from where you stand.** The phone measures the floor and what stands on it before the hunt, by eye, to within about a tenth: how tall each thing is, whether its top is level, and what is behind it. It hides a husk behind what it saw, but does not follow you walking, notice anything moved, or know what anything is. See [environment.md](environment.md).
- **The plan is the phone's word.** The server checks a plan is wide enough to be fair and has room for the husk, not that the room is really that shape. A made-up room cannot win a hunt, but it can bring the husk closer, where its seals are easier to hit.
- **Rifts trust the client.** A hunt is replayed; a rift is not. NFT reapers cannot enter until rift input replay is implemented, so trusted reports cannot mint tradable growth. The starter can still play. Making it verified means sending each seat's input log and replaying it against the shared ward's history.
- **Rifts live in one process.** Every reaper in a circle must be connected to the same server instance. Running more than one needs the room moved to shared state or the circle pinned to an instance.
- **The player is one row.** That is the right size now and will not be once a codex holds thousands of entries.
- **Models are heavy.** The six reaper models are 6 to 7 MB each, mostly from morph targets. They want trimming before a store build.
- **Receipts are not posted.** They are signed and stored; nothing on a chain reads them yet.
