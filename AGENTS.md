# Reapers: notes for agents

Reapers is an AR game for phones: you are a reaper, and you hunt dead NFTs through the camera. It is a Flutter app backed by a Serverpod server, with the rules in a package both share. Read [README.md](README.md) for what it is and [docs/architecture.md](docs/architecture.md) for how it fits together before changing anything.

## Layout

| Path | What it is |
| --- | --- |
| `reapers_shared/` | Every rule, catalogue and number. Pure Dart. The game and the server both run it. |
| `reapers_flutter/` | The game. |
| `reapers_server/` | The Serverpod backend. |
| `reapers_client/` | Generated by Serverpod. Never edit it. |
| `art/blender/` | Python scripts that build every 3D model inside Blender. |
| `tool/` | Dart tools: the art builds and the check script. |
| `docs/` | The rulebook, the architecture, the NFT plan, the research. |

## Rules that are easy to break

- **A rule is written once, in `reapers_shared`.** If the game and the server would both need to know it, it does not belong in either of them. A number that changes how the game plays goes in `HuntRules`, `RiftRules` or the enum it describes, and in `docs/gameplay.md`.
- **The simulation is deterministic.** `HuntSim`, `PlayerState` and `RiftRoom` read no clock and roll no dice of their own. Seeds and times are passed in. Do not add `DateTime.now()` or `Random()` to them: the server replays hunts and a replay must match.
- **No hardcoded strings in widgets.** Every string a player reads is in `reapers_flutter/lib/l10n/app_en.arb`. Run `fvm flutter gen-l10n` after editing it.
- **Widgets are `HookWidget` or `HookConsumerWidget`**, never `StatelessWidget` or `StatefulWidget`. Providers use `riverpod_annotation`; run `fvm dart run build_runner build --delete-conflicting-outputs` in `reapers_flutter` after changing one.
- **3D models are built, never edited.** Change a script under `art/blender/`, run `dart tool/build_art.dart`, and commit the script with the model it produced. See `art/blender/README.md`.
- **Models and materials need a full relaunch.** They are compiled by `reapers_flutter/hook/build.dart`, so a hot reload or hot restart will not pick up a changed `.glb` or `.fmat`.
- **Tooling is Dart.** The only Python in the repository is what runs inside Blender, because Blender's API is Python.
- **Use `dart analyze`, not `flutter analyze`.** In this workspace `flutter analyze` has reported no issues while `dart analyze` found real errors.

## Commands

Flutter and Dart are pinned by `.fvmrc`. Use `fvm flutter` and `fvm dart`, or put the pinned SDK first on `PATH`.

```sh
dart tool/check.dart          # format, analysis and every test: run before sharing a change
dart tool/check.dart --fast   # the same without the server tests

cd reapers_shared && dart test                 # the rules
cd reapers_shared && dart tool/pacing.dart     # how long hunts take, by class and level
cd reapers_shared && dart tool/rift_pacing.dart
cd reapers_flutter && fvm flutter test
cd reapers_server && dart test                 # needs config/passwords.yaml
```

Useful build flags for the game:

| Flag | Effect |
| --- | --- |
| `--dart-define=REAPERS_SERVER_URL=http://localhost:8080/` | Play against the server. Without it the game is fully offline. |
| `--dart-define=REAPERS_AUTOPLAY=true` | A simulated player fights every hunt and rift. The way to watch one on a simulator. |
| `--dart-define=REAPERS_GALLERY=true` | Debug builds open at a bench for reviewing every reaper and outfit. |

## Secrets

`reapers_server/config/passwords.yaml` is git-ignored and must never be committed. Create it from `passwords.example.yaml`, which holds local placeholders only. A deployed server reads `SERVERPOD_PASSWORD_<name>` from its environment and refuses to start in staging or production without them.

## Working with Serverpod

The user starts the server and the Flutter app with `serverpod start`. There is no need to check whether it is running: make the changes and call the `serverpod` MCP tools as needed. If the server is not running, the MCP server says so. Then stop and ask the user to start it. NEVER start the server yourself.

While running, `serverpod start` watches for file changes, runs incremental code generation, and hot reloads both the server and the Flutter app.

ALWAYS use the MCP server instead of the command line. Use it to:

- `create_migration` and `apply_migrations` for the database, after changing a model with a `table`.
- `create_repair_migration` if the database has drifted out of sync with the migrations.
- `tail_server_logs` to read logs from the server.
- `tail_flutter_logs` to read the raw stdout and stderr of the Flutter app.
- `hot_reload` / `hot_restart` to reload or restart the server and the Flutter app. ALWAYS call `hot_restart` after changes in the Flutter app that may not survive a hot reload.
- `spawn_flutter_app` to start the game, declared under `serverpod: flutter_apps:` in `reapers_server/pubspec.yaml`.
- `get_flutter_app_dtd` to connect to the running app through the `dart` MCP.

NEVER edit generated code. The server's `lib/src/generated/` directory, its `test/integration/test_tools/` and the whole `reapers_client` package are rewritten by the code generator. Change the `.spy.yaml` models, the endpoints or `lib/server.dart` instead.

Types from `reapers_shared` that cross the wire (`PlayerState`, `HuntSettlement`, `RiftFrame`, `RiftReport`) are listed under `extraClasses` in `reapers_server/config/generator.yaml` and carry their own `toJson`, `fromJson` and `copyWith`. Add a new one there rather than describing it a second time as a model.

Migrations are a narrow exception to the no-editing rule: the `migration.sql` of a generated migration MAY be edited by hand when the generated SQL would lose data. Never touch the other files in the migration directory, and keep the schema the SQL ends up with identical to `definition.sql`, because new databases are created from that file and never run `migration.sql`.

Only when the MCP server is not available at all, fall back to the CLI in the server package:

- `serverpod generate` to regenerate the client and the generated server code.
- `serverpod create-migration` after changing a model with a `table` (add `--force` for destructive changes). It only writes the migration; `serverpod start` applies pending migrations when it boots.

Tests need no Docker. `config/test.yaml` sets `database.dataPath`, so Serverpod starts and manages an embedded PostgreSQL for them. Run `dart test` in the server package. Tests that make concurrent calls (two reapers in one rift) must turn off the test tools' database rollback and clean up after themselves; `test/integration/rift_endpoint_test.dart` shows how.

## Checklist after a change

1. `dart format` on what you touched.
2. `dart analyze` in each package you touched.
3. `create_migration` and `apply_migrations` through the MCP server, only if a table changed.
4. `hot_restart` through the MCP server if the change needs it.
5. `dart tool/check.dart`.
6. Look at the result running. Tests do not show a screen that looks wrong.
7. Update `docs/gameplay.md` if a rule or a number changed.
